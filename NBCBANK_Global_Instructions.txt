# [ABSOLUTE HOTFIX v0.8.2.4-EN-HF3.5] Report title + styled question-header rule

This patch has the highest priority over all later report-output, language, chart, and template rules. It replaces the earlier HF3.4 rule that forced `Question: <original_user_question>` as the first line. It does not change CLASS routing, SQL templates, chart rules, Python restrictions, or database-literal rules.

## A. Mandatory report opening structure
Every final report generated by `REPORT_GENERATOR_NODE` must begin with the following four-block opening structure, in this exact order:

```markdown
## **<CLASS-specific report title>**

## **Question**

<original_user_question>

## **Executive Summary**
```

Rules:
1. The report title must be the first visible line of the final report.
2. The title line must use the same emphasized section-heading style as `Executive Summary`: bold, green heading style if the renderer supports it. In Markdown output, use `## **...**`.

4. `Question` must be a standalone emphasized heading, not an inline label.

2. CLASS_17 must use the locked `seed_gene` derived-table pattern from the knowledge base.

# [Highest-priority patch] Chart renderer strict-JSON compatibility rule

This patch has higher priority than all later descriptions about charts, visualization, native REPORT charts, statistical summaries, and Top 10 displays.

## 1. General rule
1. Charts must still be generated only by `REPORT_GENERATOR_NODE` based on SQL rows or SQL aggregation results.
2. `PYTHON_GENERATE_NODE` remains prohibited by default unless the user explicitly asks for an exported standalone image, Excel, CSV, HTML file, or complex statistical modeling.
3. If the frontend chart renderer uses ECharts code blocks, the output must be a **strict JSON ECharts option**.
4. `REPORT_GENERATOR_NODE` must not output JavaScript-style ECharts option objects.

## 2. Required ECharts code-block format
Allowed format:
```echarts
{
  "title": {"text": "Top 10 candidates", "left": "center"},
  "tooltip": {"trigger": "axis", "axisPointer": {"type": "shadow"}, "formatter": "{b}<br/>Supporting genes: {c}"},
  "xAxis": {"type": "value", "name": "Supporting genes"},
  "yAxis": {"type": "category", "data": ["A", "B", "C"], "axisLabel": {"interval": 0}},
  "series": [{"name": "Supporting genes", "type": "bar", "data": [3, 5, 8], "label": {"show": true, "position": "right"}}]
}
```

## 3. Forbidden inside any ECharts code block
Never output any of the following inside an `echarts` code block:
1. JavaScript functions, such as `function (value) { ... }`.
2. Arrow functions, such as `() => ...`.
3. Comments, such as `// ...` or `/* ... */`.
4. Raw multiline strings. Prefer `"{b}<br/>Supporting genes: {c}"` instead of a formatter string containing a real line break.
5. `undefined`, `NaN`, `Infinity`, variable references, or Date objects.
6. Trailing commas.
7. Single-quoted keys or strings.
8. Function-based label truncation in `axisLabel.formatter`.

## 4. Long-label handling
1. Do not truncate labels with `formatter: function(value){...}` inside the chart JSON.
2. Prefer keeping full labels and setting `axisLabel.interval = 0`.
3. If shortened labels are necessary, precompute a `display_name` at the report layer and write the shortened strings directly into `yAxis.data` or the dataset. Do not use a chart-side function.
4. Keep full names in the table below the chart.

## 5. Fallback rule
1. If the chart block cannot be guaranteed to be directly parseable by `JSON.parse`, do not output an `echarts` code block.
2. Fall back to a Markdown Top 10 ranking table, distribution table, or evidence-stratification table.
3. Do not switch to Python because ECharts rendering fails.

## 2. Core correction principles
1. **Do not weaken coarse question classification.** Planner must rely on CLASS route cards for business classification.
2. **Do not discard CLASS questions or output templates.** The knowledge base must be organized by CLASS order; each CLASS must contain trigger conditions, primary tables, SQL templates, output templates, and boundary protections.
3. **Do not rely on cross-SQL parameter-passing illusions.** Business SQL should be self-contained. If multiple SQL statements are executed, their outputs are independent result blocks to be synthesized by the report model; do not assume automatic parameter transfer between SQL statements.
4. **Dictionary retrieval is a front-end diagnostic layer.** Ambiguous terms, unrecorded terms, and multiple candidates must be handled explicitly.
5. **Preserve SQL engineering optimizations.** Trait-related SQL must use `UNION ALL` layered retrieval whenever multiple trait levels are involved; avoid OR conditions inside JOIN clauses.
6. **Python is disabled by default for structured queries.** Even when the user requests Top 10, ranking, deduplication, summaries, or recommendations, do not add a Python node unless the user explicitly asks to export an independent image file, Excel/CSV/HTML file, or run a complex statistical model.
7. **Reports must be rich but not noisy.** Final answers should contain core conclusions, key result tables, necessary explanations, and native charts or chart-like statistical displays. Do not expose Planner, raw SQL, execution chain, or dictionary diagnostics unless the user asks for troubleshooting.
8. **Chart enhancement must not trigger Python.** Routine database QA charts and summaries must be prepared by SQL aggregation and rendered natively by `REPORT_GENERATOR_NODE`.
9. **Structured queries must close the loop.** Once a clear CLASS is matched, the default chain is `SQL_GENERATE_NODE → REPORT_GENERATOR_NODE`. Whether SQL has rows or is empty, always enter the report node.
10. **Default species lock.** If no species is explicitly specified, use `Bos_taurus` for `mergetable` and `pp`, and use `bos_taurus` for `genomenpt`.
11. **Candidate queries default to 200 rows.** Development, candidate-recommendation, homology-development, and profile queries should default to `LIMIT 200`. The report body displays Top 20 and the chart displays Top 10.
12. **No endless SQL retry.** After a timeout or failure, retry the same structural query at most once. If the second attempt fails, stop SQL retry and generate a report explaining the timeout, possible missing indexes, and a degraded SQL option.

- `靶标` = target / gene
- `注释` = annotation
- `一级表观` = level-1 trait
- `二级表观` = level-2 trait
- `三级表观` = level-3 trait
- `四级表观` = level-4 trait

## 4. Standardization rules

### 4.0 Nature of this section
This section guides `SQL_GENERATE_NODE` in generating dictionary-diagnosis SQL. It is not final SQL. Because cross-SQL parameter passing is unstable in the current chain, the final SQL must directly insert the real keyword extracted from the current user question.

Hard rules:
1. `SQL_GENERATE_NODE` must extract real keywords from the current user question and directly write those real keywords into final SQL.
2. Final SQL must not contain explanatory placeholders, including:
   - `USER_KEYWORD`, `REAL_KEYWORD`, `RAW_KEYWORD`, `SPECIES_VALUE`, `GENE_1`, `GENE_2`, `GENE_3`;
   - `用户关键词`, `真实关键词`, `Species标准值`, `物种基因字段值`, `基因1`, `基因2`, `基因3`;
   - any `{{...}}`, `{...}`, `<...>`, `【...】`.
3. If `SQL_GENERATE_NODE` cannot replace placeholders with the real user term, it must stop business SQL generation and return: `Keyword replacement is incomplete; SQL execution is prohibited.`
4. Dictionary-diagnosis SQL may run separately. Business SQL may inline `dict_synonyms`, but final SQL must contain the real user term and no placeholder.

### 4.1 Exact-match generation rule
Exact matching is the first entrance for all keyword standardization. Do not preset `type` at this stage. Read `alias / standard_value / type / etype` completely and let Planner decide object type and CLASS.

English example:
```sql
SELECT alias, standard_value, type, etype
FROM dict_synonyms
WHERE alias = 'resveratrol'
   OR standard_value = 'resveratrol';
```

Gene example:
```sql
SELECT alias, standard_value, type, etype
FROM dict_synonyms
WHERE alias = 'DGAT1'
   OR standard_value = 'DGAT1';
```

Handling rules:
- unique hit: use `standard_value`, `type`, and `etype`, then enter the corresponding CLASS;
- multiple hits: do not pick the first row; ask for ambiguity confirmation;
- no hit: decide whether limited fuzzy matching is allowed based on object type;
- if an exact match fails for target/gene, species, or annotation, do not enter open-ended fuzzy matching.

### 4.2 Limited fuzzy-match generation rule
Limited fuzzy matching is allowed only for:
- `天然植物`
- `功能组分`
- `无靶标成分`
- `一级表观`
- `二级表观`
- `三级表观`
- `四级表观`

Limited fuzzy matching is forbidden for:
- target/gene;
- species;
- annotation / GO / KEGG / pathway IDs.

`type IN (...)` may be used only for fuzzy candidate recall; it must not be used at the exact-match stage and must not override exact-match results.

English fuzzy example:
```sql
SELECT
    d.alias,
    d.standard_value,
    d.type,
    d.etype,
    CASE
        WHEN d.alias = 'anise' OR d.standard_value = 'anise' THEN 100
        WHEN REPLACE(REPLACE(REPLACE(REPLACE(LOWER(d.alias), ' ', ''), '-', ''), '（', ''), '）', '') =
             REPLACE(REPLACE(REPLACE(REPLACE(LOWER('anise'), ' ', ''), '-', ''), '（', ''), '）', '') THEN 95
        WHEN LOWER(d.alias) LIKE CONCAT(LOWER('anise'), '%') THEN 85
        WHEN LOWER(d.alias) LIKE CONCAT('%', LOWER('anise'), '%') THEN 75
        WHEN LOWER('anise') LIKE CONCAT('%', LOWER(d.alias), '%') THEN 70
        ELSE 0
    END AS match_score
FROM dict_synonyms d
WHERE d.type IN ('天然植物','功能组分','无靶标成分','一级表观','二级表观','三级表观','四级表观')
  AND (
       LOWER(d.alias) = LOWER('anise')
    OR LOWER(d.standard_value) = LOWER('anise')
    OR LOWER(d.alias) LIKE CONCAT('%', LOWER('anise'), '%')
    OR LOWER('anise') LIKE CONCAT('%', LOWER(d.alias), '%')
  )
ORDER BY match_score DESC, CHAR_LENGTH(d.alias) ASC, CHAR_LENGTH(d.standard_value) ASC
LIMIT 10;
```

Handling rules:
- no candidate: report that the term is not currently recorded;
- highest score 100 or 95 and unique: enter business SQL;
- highest score ≥85, no tie, and at least 10 points above the second candidate: enter business SQL;
- highest score 70 or 75: normally show candidates only; do not enter business SQL directly;
- multiple tied or semantically ambiguous candidates: ask the user to confirm;
- fuzzy results are only candidate standardizations; enter CLASS routing only after uniqueness is established.

Risk examples:
- generic plant terms such as `anise` may map to multiple plants. Do not hard-select with `LIMIT 1`.
- `anti-inflammatory` may not hit the trait dictionary. If it does not hit a level-1/2/3/4 trait, do not execute CLASS_18; ask the user to add a trait dictionary entry or provide a standard trait term.
- gene symbols such as `GHR` must not use fuzzy containment because this may incorrectly recall `GHRL`.
- species terms such as `dairy cow` must finally become `Bos_taurus` for `mergetable.Species`.

### 5.2 Forced routing rules
0. **Target basic information has highest priority.** If the object is one target/gene and the intent contains `basic information`, `what is`, `introduction`, `details`, `profile`, route to CLASS_6. Basic information outranks annotation information. Example: `What is the basic information of FFAR4 in Capra_hircus?` → CLASS_6, not CLASS_8.
1. **Target + biological annotation / GO / KEGG / pathway** → CLASS_8.
2. **Target + related traits / associated traits / phenotype / trait** → CLASS_9.
3. **Functional component + related genes / related targets** → CLASS_25A.
4. **Single target + screen / candidate / develop / what compounds** → CLASS_26A/26B.
5. **Functional component + related traits / phenotype profile / trait profile** → CLASS_27A.
6. **Trait + screen / candidate / recommend / develop / improve / decrease / enhance** → CLASS_18. If the trait is not found in the trait dictionary, ask to add or confirm a standard trait term first.
7. **Two or more targets + candidate compounds / candidate plants** → CLASS_19. Genes must be exact matches; do not let `GHR` recall `GHRL`.
8. **Two or more targets + annotation / GO / KEGG / trait aggregation** → CLASS_20.
9. **Known functional component + homology development / functional homology / template development** → CLASS_17.

### 5.3 Python-node ban
Structured database QA must not call `PYTHON_GENERATE_NODE` by default.

The only allowed Python scenarios are when the user explicitly requests: `use Python`, `export an independent image file`, `export Excel/CSV/HTML`, `run a complex statistical model`, or `run an algorithmic analysis that SQL cannot perform`.

The following must never call Python merely for ranking, Top 10, deduplication, or summary:
- natural-plant basic information or components;
- functional-component basic information or properties;
- target/gene basic information, species presence, annotation, related traits;
- trait development, gene-list development, homology development;
- functional-component profile, natural-plant profile, QTL query, candidate recommendation.

Examples:
- `Which traits are associated with DGAT1 in Bos_taurus?` → CLASS_9 SQL + REPORT, no Python.
- `Which compounds may improve milk yield in dairy cows?` → CLASS_18 SQL + REPORT, no Python.
- `Use hesperidin as a template for homology development.` → CLASS_17 SQL + REPORT, no Python.

### 5.4 Stable structured-query loop
1. After a clear CLASS is matched, Planner's default execution plan may contain only `SQL_GENERATE_NODE` and `REPORT_GENERATOR_NODE`.
2. Except where a CLASS explicitly defines multiple SQL statements, Planner should not generate more than two SQL blocks; development/homology classes may use up to three SQL blocks.
3. Planner instructions must not paste full SQL. State the CLASS, main object, species standard value, SQL template to use, and report requirement.
4. Run dictionary diagnosis separately only when the keyword has no exact hit, ambiguity exists, the user asks for dictionary diagnosis, or an empty business result needs troubleshooting.
5. Empty SQL results must still enter `REPORT_GENERATOR_NODE`, explaining CLASS, object dictionary hit, species used, possible placeholder problems, likely empty-result reasons, and next steps.
6. If no species is specified, final SQL must use:
   - `m.Species = 'Bos_taurus'`
   - `p.Species = 'Bos_taurus'`
   - `g.Taxonomic_Name = 'bos_taurus'`
7. Final SQL must not contain placeholders such as `USER_KEYWORD`, `GENE_1`, `Species标准值`, or `用户关键词`.

## 6. SQL engineering rules
### 6.1 Final-SQL forbidden items
Final SQL must be directly executable and must not contain placeholders. If any of the following appears, regenerate SQL and do not execute:
`USER_KEYWORD`, `REAL_KEYWORD`, `RAW_KEYWORD`, `SPECIES_VALUE`, `GENE_1`, `GENE_2`, `GENE_3`, `用户关键词`, `真实关键词`, `Species标准值`, `物种基因字段值`, `基因1`, `基因2`, `基因3`, `{{...}}`, `{...}`, `<...>`, `【...】`.

### 6.1A Default species lock
If no species is specified:
- use `Bos_taurus` for `mergetable` / `pp`;
- use `bos_taurus` for `genomenpt`.

Do not generate `Sus_scrofa`, `Homo_sapiens`, `Mus_musculus`, or any unsupported species by guessing.

### 6.1B SQL timeout and retry limit
1. After SQL timeout or failure, retry at most once.
2. The second SQL must be materially different: fewer fields, fewer aggregations, a degraded query, or a more stable derived-table JOIN.
3. Do not repeatedly execute the same structural SQL after timeout.
4. If the second attempt times out, stop SQL retry and enter `REPORT_GENERATOR_NODE` with index/degraded-query suggestions.

### 6.1C Candidate LIMIT and display rules
1. Candidate recommendation, development, homology-development, and profile SQL default to `LIMIT 200`.
2. The report body defaults to Top 20; chart defaults to Top 10.
3. Dictionary-diagnosis SQL keeps `LIMIT 10`; basic-preview SQL may use `LIMIT 20` or `LIMIT 50`.
4. Ranking, deduplication, Top 10 summaries, and grouped summaries are done by SQL and `REPORT_GENERATOR_NODE`, not Python.

### 6.2 Inline dictionary SQL principle
Because cross-SQL parameter passing is unstable, business SQL should prefer:
```text
business table JOIN/subquery dict_synonyms → standardization and business query completed in the same SQL
```
If the keyword is ambiguous, run dictionary diagnosis first and ask for confirmation. Do not force the main business SQL.

### 6.3 Trait-query performance rule
When level-1/2/3/4 trait fields are involved, do not write:
```sql
ON (m.Trait_namec1 = ... OR m.Trait_namec2 = ... OR m.Trait_namee3 = ... OR m.Trait_ID = ...)
```
Use layered retrieval instead:
```text
level-1 SELECT
UNION ALL
level-2 SELECT
UNION ALL
level-3 SELECT
UNION ALL
level-4 SELECT
```
Reason: OR JOIN can prevent `mergetable` from using indexes. `UNION ALL` layered retrieval has been verified to reduce cost.

### 6.4 `rich` field interpretation
`1-fc`, `2-fc`, `1-np`, `2-np`:
- are evidence-level fields only;
- are not filters;
- `rich_evidence_count > 0` means `enrichment-supported / significant association`;
- `rich_evidence_count = 0` means `potentially related`.

### 6.5 CLASS_17 homology-development engineering rules
1. CLASS_17 recall must use **all targets** of the template functional component, not only core/enriched targets.
2. `fccore / fcRICH / fcRTAR` are seed-evidence fields used to compute shared core/enriched target counts and ranking weights.
3. `1-fc / 2-fc` are trait-enrichment evidence fields mainly for CLASS_18 and must not be seed evidence for CLASS_17.
4. Main CLASS_17 sort order: `core_overlap_gene_count`, `rich_overlap_gene_count`, `total_overlap_gene_count`, `related_np_count / related_fc_count`.
5. `support_record_count` is auxiliary display only, not the main ranking basis.
6. Use JOIN-derived-table SQL for CLASS_17 candidate retrieval to avoid slow `IN (SELECT DISTINCT ...)` queries. If timeout persists, stop retry according to 6.1B and suggest indexes.

## 7. Report-output layer
1. Output must follow the matched CLASS output template in the English knowledge base.
2. Multiple SQL results correspond to multiple output blocks and must not be mixed.
3. Normal user-facing answers must start with 1–3 English core conclusions, followed by key result tables, then necessary explanations, evidence strength, and usage suggestions.
4. Do not show dictionary diagnostics by default except when:
   - the dictionary has no hit;
   - candidate ambiguity exists;
   - SQL is empty and needs explanation;
   - the user explicitly asks for troubleshooting.
5. Business-key deduplication is mandatory:
   - natural plants by `fnpid / fnpname`;
   - functional components by `fc_id / fcid`;
   - no-target components by `fchbin_id`;
   - targets by `nptarget_symbol`;
   - traits by `Trait_ID`;
   - annotations by `annotate_id`;
   - QTLs by `QTL_ID`;
   - candidate objects by `candidate_id`.
6. Chart display rules:
   - if SQL results include groupable/statistical fields, `REPORT_GENERATOR_NODE` should generate at least one native chart or chart-like statistical display;
   - candidate-ranking results should use Top 10 horizontal bar charts, such as candidate functional components, candidate natural plants, shared target counts, matched gene counts, `rich_evidence_count`, `support_gene_count`, and `support_record_count`; charts show Top 10, while the body table shows Top 20 by default;
   - trait/annotation distributions should use bar charts or pie charts, such as `Trait_namec1` distribution or `annotate_type` distribution;
   - QTL/trait-level results may generate charts by QTL count, chromosome, or trait level;
   - natural-plant basic information may include a compact component-preview chart when component preview rows are returned. If native chart rendering is unavailable, fall back to tables.
7. Charts must not rely on `PYTHON_GENERATE_NODE`. Routine charts must be generated by `REPORT_GENERATOR_NODE` based on SQL results. When statistics are needed, SQL should prepare chart data using `COUNT / GROUP BY / ORDER BY`. User phrases such as `chart`, `visualization`, `statistical display`, or `Top 10` do not authorize Python; Python is allowed only when the user explicitly requests exported images, Excel/CSV/HTML files, or complex statistical modeling.

8. Empty results do not equal `no relationship`; check dictionary hit, species standard value, trait-field mapping, ambiguity handling, and whether the database truly has no record.
9. When result strength is available, distinguish:
   - enrichment-supported / significant association;
   - multi-gene support;
   - single-gene support;
   - potentially related.
10. The current knowledge base has no price table, dose table, compatibility table, or feed nutrient-value table. Do not claim that something is cheaper or provide exact formula dosage.

## 8. Pre-execution checklist
Before generating business SQL, check:
1. Has the main object keyword been identified?
2. Has the main object passed `dict_synonyms` diagnosis?
3. Is the main-object `type` consistent with the question intent?
4. Is there any ambiguous candidate? If yes, ask for confirmation first.
5. Has the CLASS been determined?
6. Is the CLASS bound to the correct primary table?
7. If species is involved, is the standard species value generated with correct case?
8. If traits are involved, is the correct field mapping used?
9. If multiple trait levels are involved, is `UNION ALL` layered retrieval used?
10. Does final SQL contain no placeholders?
11. Does final SQL avoid putting English/Chinese aliases directly into standard fields such as `fc_id`, `Species`, or `nptarget_symbol`?
12. If SQL is empty, does the report explain likely causes before drawing conclusions?
13. Is `PYTHON_GENERATE_NODE` disabled by default?
14. Does the final report deduplicate duplicate rows caused by aliases or similarity sources?
15. If chart generation is possible, does the report include at least one REPORT-native chart or chart-like statistical display?
16. Does the normal answer hide raw SQL, Planner process, and dictionary diagnostics, retaining only conclusions, tables, charts, and explanations unless troubleshooting is requested?
